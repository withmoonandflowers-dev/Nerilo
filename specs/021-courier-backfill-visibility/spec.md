# Spec 021：讓信使補回的訊息出現在聊天畫面

- 軌別：feature
- 狀態：planned
- 建立：2026-08-08／最後更新：2026-08-08
- 關聯：ADR-0023（房間即複寫日誌）、ADR-0024（盲信使代管）、Spec 001、Spec 013

## 1. 要做什麼、為什麼（specify）

一個離線過的成員回線之後，應該在聊天畫面上看到自己不在時別人發的訊息，順序正確、各一次。

現在看不到。2026-08-07 到 08 的實測（三個獨立瀏覽器設定檔、正式 Firebase 專案）確認傳輸層整條是通的：寄件者把密文寄存給陌生節點、收件者回線與該節點對帳、紀錄通過驗簽與世代閘門後落地收件者的複本庫，金鑰也對得上（紀錄與收件者重載後裝回的房間金鑰同為 `ep=0`）。但進房之後畫面上只有斷線前那一則。訊息在收件者的硬碟上，解得開，沒有任何路徑把它送到畫面。

沒有它會怎樣：盲信使這條線在使用者眼中等於不存在。專案對外的主敘事是「斷網情境下訊息仍送達」，補助與競賽的 demo 全押在這一幕，而這一幕現在演不出來（見 `對外申請素材/Nerilo/03_Demo動線腳本_5分鐘.md` 第二節）。ADR-0023 把房間定義為永續複寫日誌，日誌有資料而畫面讀不到，是這個定義沒有落實到呈現層。

**憲法檢核**（constitution.md）：

- 目標函數加分項：**補助競爭力**（demo 主線能不能演，直接決定 InnoServe 與 APICTA 的說服力）與**隱私韌性**（離線送達是韌性主張的實質內容，不是修辭）。可嵌入也沾邊：SDK 消費者拿到的行為應與參考應用一致。
- 四條不變量影響：
  - **恰好一次**：**有影響，是本 spec 的主要風險**。補回的紀錄進入呈現層之後，必須維持「每則訊息在每個畫面上恰好一次」。兩條供給路徑（既有歷史來源與補回路徑）同時存在時容易造成重複，驗收必須直接釘住這條。
  - **E2EE 機密性**：無影響。不動加解密，也不動 keyx 重放語義；呈現層沿用既有的解密與佔位規則。
  - **點數帳本正當性**：無影響。不動寄存經濟、報價與額度。
  - **身分與授權**：無影響。補回的紀錄在落地前已經過驗簽、公鑰與身分綁定、世代門檻三道閘（`runCourierBackup` 的 ingest），本 spec 不放寬任何一道。

## 2. 邊界（明確不做）

- 不改信使協議的線上格式。本案不是 protocol 軌，QUOTE、欠條、sync 與 records 的欄位一律不動。
- 不改 React 產線。該產線已凍結待退役（ADR-0017），只在 Vue 線收斂。
- 不動寄存經濟：額度、計價、欠條與拒收語義維持現狀。
- 不擴大補歷史的範圍。Spec 009 已拍板放棄跨會話補歷史，本案不回收該能力。
- 不處理跨裝置備份、私鑰復原與多副本合併。
- 不改 `hydrate()` 既有的金鑰環重建與 keyx 重放行為。
- 不改盲信使「只在 dashboard 掛載時運作、背景備份 30 秒一輪」的既有節奏。補齊時間的穩定性是另一件事，本案不處理。

## 3. 待釐清（clarify）

全部已拍板（2026-08-08 使用者裁決），決議如下，無殘留歧義。

- [x] Q1 方向：**歷史來源改讀複本庫**，聊天儲存從歷史來源退役。合 ADR-0023「房間即複寫日誌」的原意，一次消掉兩個庫分歧的整類問題。**代價已知並接受**：這會動到 SDK 公開契約（`IChatStorage` 是 `src/sdk/index.ts` 匯出的型別，`storage` 是 `createChatClient` 三個可注入後端之一），範圍與風險都大於補派解。提問時已標明較保守的補派解可較快解除 demo 阻塞，使用者選擇架構解。
- [x] Q2 聊天儲存的處置：隨 Q1 決議，不再作為歷史來源。注入縫如何收斂見第 4 節，屬重大取捨，完成後回填 ADR-0038。
- [x] Q3 未讀：**連未讀一起補**。補回的訊息參與未讀標記與已讀水位計算。
- [x] Q4 排序：**沿用既有因果順序原語**，與即時到訊同一套，不新增排序邏輯。
- [x] Q5 非 chat 通道：**一併處理**。補回的表情與已讀回報也套進既有聚合。

## 4. 技術計畫（plan）

### 4.1 核心決定

歷史的唯一真相來源改為複寫日誌（複本庫）。`loadHistory()` 不再讀聊天儲存，改由 `IGossipPersistence.loadRoom()` 取出紀錄，經解密與投影後回傳。

這一步把「同一則訊息有兩個獨立寫入者、兩個獨立讀取者」的結構拆掉。信使補回的紀錄之所以看不到，根因就是它只餵到其中一個庫。

### 4.2 單一投影

現在 `GossipMessage` 轉 `ChatMessage` 的邏輯內嵌在 `MeshChatService` 的到訊處理函式裡。抽成 `core/messaging` 的純函式，即時路徑與歷史路徑共用同一份，避免兩條路投影出不同結果。

一個必須參數化的差異：即時路徑會濾掉自己的訊息（本機已樂觀顯示，避免回音重複），歷史路徑**不能濾**，否則使用者看不到自己過去發過的話。這是最容易寫錯的一點，驗收要直接釘住。

### 4.3 解密與佔位

歷史路徑在投影前必須走 `RoomContentKeyRing.toDisplayMessage`，與即時路徑同一條路，包含無金鑰時的佔位字串。不得在歷史路徑另寫一套解密。

### 4.4 通道分流（Q5）

replay 時按 `channel` 分派，與即時路徑一致：`chat` 進泡泡；`reaction` 與 `read` 分別餵進既有的兩個 reducer；`keyx` 跳過（`hydrate()` 已處理，重複消費無益）；`game` 跳過（PARK 模組，不在本案範圍）。

### 4.5 排序（Q4）

投影後交既有的因果順序原語處理，與即時到訊同一套。因果依賴與邏輯時鐘存在於內容裡，所以順序必須在解密之後才算得出來，這決定了 4.3 與 4.5 的先後。

### 4.6 未讀（Q3）

補回的訊息要參與未讀計算。這裡有一個新語義要定義：現行未讀綁 Firestore 的房間活躍時間戳，而複本庫是本機資料，兩者不是同一個時間軸。方案是以「本機已見水位對比複本庫最新紀錄」判定未讀，讓未讀不再依賴中央欄位。這是本案唯一新增的語義，任務標 ⚠。

### 4.7 SDK 公開表面（重大取捨，回填 ADR-0038）

`IChatStorage` 與 `InMemoryChatStorage` 目前由 `src/sdk/index.ts` 匯出，`storage` 是 `createChatClient` 的注入縫之一。歷史改讀複本庫之後，這個縫的語義不再成立。

採「換縫」而非「留著不用」：移除 `storage` 注入縫，改開複本持久層的注入縫（`IGossipPersistence` 的必要子集，不整個攤開）。理由是留一個宣稱可注入、實際不影響任何行為的縫，比移除它更糟，採用方會據此做出錯誤假設。

這是破壞性變更。可行的前提是版本停在 0.9.0、尚未發佈到套件庫、零外部採用方，現在改是最後一次便宜的機會。`docs/SDK-QUICKSTART.md` 與 `examples/minimal-chat` 要同步改，`qa:pack-smoke` 與 `qa:sdk-isolation` 兩道 CI 閘門必須維持綠。

### 4.8 相容與遷移

既有房間的歷史可能只存在於聊天儲存，而複本庫因為 floor 淘汰或 legacy 零代紀錄而不完整。過渡策略：本版保留一次性搬遷，開房時若偵測到聊天儲存有而複本庫沒有的訊息，就地補進複本庫後再走新路徑；搬遷完成即不再讀聊天儲存。搬遷必須冪等，且失敗不得擋住進房。

### 4.9 不動的部分

React 產線凍結（ADR-0017），其 `features/chat/ChatService.loadHistory` 不改。SDK 的 `IChatEngine.loadHistory()` 簽章與回傳型別不變，只有資料來源改變，所以 `NeriloClient` 的公開行為對呼叫端維持相容。

## 5. 任務分解（tasks）

改運作中路徑的任務標 ⚠，動手前走 `harden-tests`（characterization-first、分層閘門、誠實條款）。

- [ ] T1 ⚠：抽出 `GossipMessage` 轉 `ChatMessage` 的單一投影純函式（含「是否濾自己」參數），即時路徑改用它。純重構，行為不變，先以現況測試釘住。
- [ ] T2 ⚠：`loadHistory()` 改由複本庫投影，經 `toDisplayMessage` 解密，含自己發過的訊息。
- [ ] T3 ⚠：replay 的通道分流，`reaction` 與 `read` 餵進既有 reducer，`keyx` 與 `game` 跳過。
- [ ] T4 ⚠：歷史投影接既有因果順序原語，斷言與即時路徑排序一致。
- [ ] T5 ⚠：未讀改以「本機已見水位對比複本庫最新紀錄」判定（4.6 的新語義）。
- [ ] T6 ⚠：SDK 表面換縫。移除 `storage`，開複本持久層注入縫；同步改 `docs/SDK-QUICKSTART.md` 與 `examples/minimal-chat`；`qa:sdk-isolation` 與 `qa:pack-smoke` 維持綠。
- [ ] T7：舊資料一次性搬遷（冪等、失敗不擋進房）。
- [ ] T8：端到端迴歸鎖。三個獨立瀏覽器設定檔，寄件者與收件者從未同時在線，訊息經陌生節點代管後出現在收件者畫面。
- [ ] T9：回填 ADR-0038（SDK 注入縫換縫的決策與取捨），更新 `docs/CURRENT-STATUS.md`。

## 6. 驗收（黃金判準）

- [ ] V1（本案目標）：寄件者與收件者從未同時在線，收件者回線後在聊天畫面上看到離線期間的全部訊息，順序正確。對應 T8 的 E2E。
- [ ] V2（恰好一次）：上述訊息在畫面上各恰好一次；既有訊息不因為改來源而重複。沿用既有矩陣測試的斷言方式（count 等於一，同時抓漏與重）。
- [ ] V3（自己的歷史不掉）：收件者重載後看得到自己過去發過的訊息（4.2 的參數化差異寫錯就會紅）。
- [ ] V4（解密一致）：無金鑰的紀錄在歷史路徑顯示與即時路徑相同的佔位字串，不是消失也不是拋錯。
- [ ] V5（其他通道）：離線期間的表情與已讀回報，回線後正確套進聚合。
- [ ] V6（未讀）：離線期間收到的訊息讓房間列表亮未讀，打開後熄滅。
- [ ] V7（不迴歸）：`@vue-stable` 全綠；`npm run ci` 全綠；`qa:sdk-isolation` 與 `qa:pack-smoke` 綠；React 線不受影響。
- [ ] V8（遷移）：既有房間升級後歷史不減少，重複執行搬遷不產生重複訊息。

- [x] 第 5 節任務完整實現第 4 節，無遺漏。4.1 對 T1 與 T2、4.4 對 T3、4.5 對 T4、4.6 對 T5、4.7 對 T6、4.8 對 T7；T8 與 T9 是驗收與回填。
- [x] 第 6 節驗收能證明第 1 節。V1 直接驗使用者情境而非模組行為；V2 與 V3 釘住兩個最可能寫錯的地方（重複、濾掉自己）；V4 到 V6 對應拍板的三個範圍決定。
- [x] 未違反憲法任何一條。第 4 條：四條不變量的影響已在第 1 節逐條聲明，恰好一次是主要風險且有 V2 直接驗。第 6 條：所有動運作中路徑的任務已標 ⚠ 並指定走 harden-tests。第 7 條：SDK 公開表面的變更為顯式決策，回填 ADR-0038（T9），不是默默改。第 14 條：本案碰不變量與 SDK 表面，已先 spec 後實作。
