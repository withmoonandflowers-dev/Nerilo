# Spec 025：讓嵌入者共享房間狀態（含晚進者補齊）

- 軌別：feature
- 狀態：done（2026-08-24 同日完成，V1-V5 驗收過）
- 建立：2026-08-24／最後更新：2026-08-24
- 關聯：Spec 023（transport 入口）、Spec 009（前向保密取捨）、2026-08-24 資料類型盤點（六類之四）、ADR-0031（PARK 圍籬／SharedDataStream 現況）

## 1. 要做什麼、為什麼（specify）

資料類型盤點（2026-08-24，使用者拍板「按資料類型分類讓開發者易用」方向）指出六類資料中「共享狀態」是最大缺口：記分板、房間設定、大廳出席表、協作文件的游標表——任何「晚進的人要拿得到現況」的東西，目前嵌入者都得自己刻快照協議。這是回合制、大廳型、協作型應用共同的前置工程。

要補一個小的狀態原語：**房間級共享狀態物件，成員改了大家看得到，晚進者連上就拿得到現況**。

**兩條先行結論（specify 期查證，決定本 spec 的形狀）**：
1. `SharedDataStream`（hash 鏈日誌）不是本 spec 的地基：其管理層 core/chain 已於 2026-07-26 因零引用刪除，本體從未接進產品流；把它開上公開表面＝宣稱未經產線驗證的能力（憲法第 10 條、洋蔥路由事件的教訓）。
2. **日誌重放這條路對晚進者天生不通**：Spec 009 前向保密下，晚進者開不了加入前的密文。正確原語是**快照＋增量**——晚進者向在場成員索取以現行金鑰密封的狀態快照，之後跟增量。

**憲法檢核**（constitution.md）：
- 目標函數加分項：**可嵌入**（六類資料盤點的最大缺口，回合制/大廳/協作應用的共同前置）；補助競爭力（「層」的完整性敘事）。
- 四條不變量影響：恰好一次〈無影響：狀態層用 LWW 冪等收斂，不依賴恰好一次，重送無害〉；E2EE〈**有**：快照與增量一律走既有 raw 通道的房金鑰密封（Spec 023 管線），不開新明文面；且快照語義與 Spec 009 前向保密一致——晚進者拿到的是「現況」不是「歷史」，看不到加入前的過程〉；帳本正當性〈無影響〉；身分授權〈無影響：狀態參與者＝mesh 房間成員，沿用既有成員資格〉。

## 2. 邊界（明確不做）

- 不做 CRDT／OT（並發編輯收斂）：衝突語義為 per-key LWW（HLC 時戳裁決），文件明示「高頻並發改同一 key 會互蓋」；要 CRDT 的應用自帶（狀態值是不透明 JSON，放得下 CRDT 材料）。
- 不做持久化：狀態活在會話中，全員離開即消失（要持久拿去自己的後端存）。
- 不做跨房間／全域狀態。
- 不動 `SharedDataStream`／PARK 圍籬（它繼續凍結，本 spec 不救它也不刪它）。
- 不做權限分級（誰可寫哪些 key）：全成員可寫任意 key；需要權限的應用在 app 層驗證。

## 3. 待釐清（clarify，2026-08-24；使用者已拍板方向「簡單易用優先」，以下為技術判斷，由提案者決定並記錄）

- [x] **Q1 衝突語義**：per-key LWW，HLC（邏輯時鐘）時戳＋senderId 決勝（時戳同則 id 大者勝，全端一致）。理由：目標使用者是「想快點做出遊戲」的開發者，LWW 好懂、冪等、重送安全；CRDT 的成本與心智負擔不成比例（邊界已列明）。
- [x] **Q2 掛在哪**：`NeriloTransportClient`（遊戲/低延遲入口）。理由：需要它的場景（大廳、回合制、協作）正是 transport 的目標客群；實作只需 raw 通道（可靠模式）＋peers，零訊息層依賴。聊天客戶端要用可之後再橋（形狀不阻擋）。
- [x] **Q3 快照來源**：晚進者向「任一已連上的 peer」索取（先到先用）；不設協調者。理由：2-10 人房任一在場成員的狀態在 LWW 收斂下等價；選協調者引入選舉與失效處理，違反簡單優先。
- [x] **Q4 大小上限**：單 key 值 ≤ 8KB、全狀態 ≤ 64KB（快照要在一則可靠通道訊息內送完，對齊在線送達既有口徑）。超限拋錯（fail-visible），不靜默截斷。

## 4. 技術計畫（plan）

### 4.1 契約（`nerilo/transport` 增）

```
NeriloTransportClient 增：
  sharedState(): SharedState        // 每 client 一顆（lazy 單例）

SharedState {
  get(): Record<string, unknown>                  // 目前收斂視圖（深拷貝）
  set(key: string, value: unknown): void          // 寫一鍵（廣播增量；金鑰未就緒丟棄+計數）
  delete(key: string): void                       // 刪鍵（墓碑增量）
  onChange(cb: (state, changedKeys: string[]) => void): () => void   // 訂閱當下先收一次
  dropped(): number                               // fail-visible：被丟棄的出站增量計數
}
```

### 4.2 線上協議（騎 Spec 023 raw 通道，可靠模式）

- 每對 peer 開（或複用）一條 `raw:state` 通道（`{ordered:true}`，不限重傳＝連線存續期間可靠保序）。
- 三種訊息（JSON 字串，經 raw 通道房金鑰密封，繼承 raw-v1 格式）：
  - `{t:'d', k, v?, hlc, from}`：增量（set/delete；delete 無 v，以墓碑記錄）。
  - `{t:'q'}`：快照請求（晚進者連上後發）。
  - `{t:'s', state, hlcs}`：快照回應（全狀態＋各 key 的 HLC 裁決材料）。
- LWW 套用規則（純函式，單元直測）：`(hlc, from)` 字典序大者勝；快照與增量走同一套用函式 → 亂序/重複/快照與增量交錯全部收斂。
- 墓碑保留於會話存續期間（防止「刪除被舊增量復活」）；不持久化故無墓碑回收問題。
- 新 peer 連上（onPeerChange）：向其發 `q`；收到多份快照全部套用（LWW 冪等，多來源無害）。

### 4.3 取捨

- 騎 raw 通道而非另建協議層：加密、通道生命週期、丟棄語義全部繼承 Spec 023 已驗證管線；本 spec 的新面只有「LWW 純函式＋三種訊息」。
- 每 peer 一條 state 通道（非廣播樹）：2-10 人房 n-1 條可靠通道成本可忽略，換到「無中繼節點單點」。
- 前向保密一致性：快照只含「現況」，晚進者天生看不到歷史過程——這不是限制而是與 Spec 009 對齊的隱私性質，文件如此陳述。

〔實作期修訂（4.2 補三則，全部由實測揪出）〕
① 入站 state 通道在本端尚未呼叫 sharedState() 時**緩衝待領**，不得關閉——對端視通道
已建立、不會重開（首版「無消費者即關」策略造成 A 的廣播永遠沒有出口）。
② 通道開啟時**雙向互發 q+s**（不只 q）：讓「通道曾斷開重建」立即 re-sync。
③ **金鑰事件驅動的 re-sync**：q/s 在金鑰未就緒窗被 raw 管線丟棄（Spec 023 語義，正確），
且晚進者有同代異鑰窗（Spec 022 已知：自選產生方各持異鑰，keyx 交接後 epoch 跳代）——
狀態層在 encryption 轉 ready 與送出金鑰 epoch 變化時對全部 outbound 重發 q+s
（LWW 冪等，多發無害）。StateTransportPort 因此增 onStatus 與 currentEpoch 兩面。
